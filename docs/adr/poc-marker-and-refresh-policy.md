# Accepted POC indicators and generalized incoming-mail processing

On 30 October 2026 the owner explicitly accepted two optional POC rules: the known MCP marker, including header-spoofing false positives; and the Gmail API indicator, including false positives from ordinary API scripts/automation. These choices change the earlier requirement to wait for authenticated Send evidence on those demo routes. Neither option is enabled by default in new configurations.

`known_mcp_marker_poc_enabled` permits `sender-rules/known-mcp-marker-poc/v1`: exactly one known `x-ai-generated: mcp-office365` declaration in a complete, non-conflicting technical-header snapshot. `gmail_api_agent_poc_enabled` permits `sender-rules/gmail-api-indicator-poc/v1`: one unique Gmail API HTTPREST Received hop. Identical provider-repeated transport headers are deduplicated; distinct/conflicting hops are not merged into proof. Their evidence references are header/transport digests, with `header_indicator` attribution. They do not assert verified agent execution or identify a specific vendor. Contradictory authenticated source evidence, incomplete inspection, unrelated/duplicate markers and conventional automation remain guarded. The authenticated Claude and registered-application rules remain separate.

The accepted indicators are spoofable or nonspecific and are excluded from the strict detector's population accuracy qualification. A matching ordinary Gmail API script can receive AI Agent in the optional mode. A copied MCP header can also cause a false positive. No measured population false-positive rate or universal agent detection is claimed.

Human rule v3 follows the owner-approved normal-client compatibility policy independently of writing style. A clean complete snapshot remains Human during routine audit waits/refreshes. Conflicts, version mismatches, stale affirmative execution evidence and explicit source errors remain guarded. A headerless agent can initially appear Human before authenticated evidence arrives, and browser-controlled agents can remain Human under that compatibility policy. Indicator explanations are independent of non-conflicting audit refresh status so refreshes do not create label churn.

The owner subsequently required **every incoming email regardless of subject/body**. That instruction supersedes the synthetic-prefix boundary and the temporary message-ID exceptions. Both filters are removed from the runtime model and pipeline; legacy configuration keys are discarded during migration. Previously filtered messages are rehydrated while retaining the same delta checkpoints and mutation journal. New incoming mail from every sender uses the same rules. The recorded history cutoff and receiving-folder/draft boundaries still apply. This authorizes local header-only processing and category annotation in the already scoped mailbox, without bodies, attachments or another mailbox grant.

The mail API does not select subject/body properties. The RFC Subject header is excluded from classification snapshots. Test subjects, content, labels and action reports are not classifier inputs. Controlled tests use owner action reports only as external ground truth.

Continuous analytical audit work runs in one separate thread in the same Python process with distinct transport/token-provider instances. SQLite transactions/closure are serialized, and late network results cannot write after shutdown. New observations yield promptly to classification/annotation; redundant repeat collection polls and idle pauses while work is ready are avoided. Transient reads retain durable jobs with capped backoff and Retry-After compliance instead of becoming permanent omissions. An independently verified message is not starved by another folder's failure. Mutation conflicts/ambiguity retain conservative bounds and readback safeguards.

The live profile uses a one-second idle pause and two-second delta interval. These are settings, not an instant-display guarantee. Decision-to-server confirmation is measured separately from receipt-to-ingestion and Outlook client refresh. The owner observed approximately five to six seconds for custom Gmail manual/Claude messages before the final handoff optimization. Native client caching can add time; read-state/content are never modified to force refresh.

Policy/mode changes requeue current observations. Both persistence and annotation recompute the selected policy, so disabling an optional rule prevents reuse of its old decision. Historical assessments remain historical. The existing one-mailbox identities, category ownership and conditional endpoint qualification are reused. No email-send capability, new application/grant, Windows account/service or Azure resource is added. The old experimental terminal script is not imported.
